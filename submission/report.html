Assumptions

  • Target users: Digital advertising operations teams — Ad Ops, Campaign Managers, and human Reviewers. Not intended as a self-service consumer product.
  • Primary cloud: AWS. Azure and GCP equivalents are fully documented in Section 8.
  • Implementation status: Baseline/POC is complete as of 2026-07-10. This submission covers MVP-to-Production architecture. The code demonstrated is production-oriented (FastAPI + XGBoost + RAG service), not a throwaway prototype.
  • LLM provider: AWS Bedrock (Claude Sonnet for RAG, Claude Haiku for explanations) in MVP. GPT-4o via Azure OpenAI private link is documented as an alternative.
  • Crawl compliance: Targets are third-party ad inventory URLs. Legal review and robots.txt compliance are handled per jurisdiction; the platform respects configurable rate limits and user-agent identification.
  • Gold-label dataset: 615 URLs from internal Ad Ops review. Vendor blocklists (Jounce, IAS) are used only for bootstrap labelling, never as sole ground truth.
  • Traffic enrichment: Features such as paid_traffic_pct require a Similarweb-style third-party API. These are treated as one signal tier, not source of truth (ADR-008).
  • Baseline targets: Precision ≥ 85%, Recall ≥ 70% on the gold-label set. The MVP feature expansion (16 → 60 features) is designed to close any remaining metrics gap.

1. System Architecture

The MFA Detection Platform is designed around a single core principle: no single signal is sufficient to identify a Made-For-Advertising site. MFA operators invest heavily in surface-level evasion — clean homepages, valid IVT profiles, even acceptable viewability scores. The platform's defensive architecture therefore scores at URL/page-section granularity using a multi-layer evidence accumulation strategy that combines crawl observations, domain metadata, supply chain signals, and campaign performance anomalies.

The pipeline is structured as an 8-layer system, each layer producing versioned, auditable artifacts. The ingestion layer normalises and deduplicates incoming URLs, assigning a deterministic url_id via UUID5 before enqueuing them for asynchronous processing. The signal extraction layer employs a dual-persona Playwright crawler that simulates both direct navigation and content-recommendation referral (Outbrain/Taboola-style), capturing the referral-versus-direct behavioural delta that is one of the strongest MFA indicators per IAB/IAS guidance. A 60-second dwell period captures ad refresh behaviour that only manifests over time.

The AI/ML layer is deliberately hybrid: a deterministic rules engine fires first on known high-precision patterns, short-circuiting the ML model when confidence is already high. When the rules engine passes, an XGBoost ensemble trained on the gold-label dataset produces a calibrated probability that feeds into a 5-tier output: MFA_High, MFA_Medium, MFA_Low, Non_MFA, and Uncertain. The LLM is intentionally not in the classification path (ADR-001); it is used only for human-readable explanation generation and for the RAG bot. This preserves auditability, keeps inference costs predictable, and makes the classifier's decisions fully reproducible.

Every decision in the pipeline is bound to its evidence via a SHA-256 hash of the canonical signal snapshot JSON (evidence_hash). This hash travels through classification, explanation, RAG responses, and audit events, forming an immutable chain of custody that supports compliance requirements. The HITL review queue routes medium-confidence and high-spend-uncertain cases to human reviewers whose overrides are stored alongside (never replacing) the ML score, preserving the ML signal for model retraining.

The classification pipeline follows a strict cascade pattern designed to maximise precision while keeping computational cost proportional to uncertainty:

  1. Rules Engine — Deterministic evaluation against high-precision rules (e.g., ad_to_content_ratio > 0.65 AND content_word_count < 250). When a rule fires, the pipeline short-circuits with classifier="rules" and confidence="high". No XGBoost inference required, no calibration step. This path handles ~20–30% of MFA_High cases at near-zero compute cost.
  2. XGBoost Ensemble — When no rule fires, the full 16-feature vector is passed to the trained XGBoost classifier. predict_proba() returns a raw probability in [0,1]. The model is trained on domain-split data (train/val split by domain, not URL, to prevent leakage). SHAP values are computed for the top-5 contributing features.
  3. Confidence Calibrator — Raw XGBoost probabilities are systematically overconfident. An Isotonic regression (or Platt scaling) calibrator trained on the validation set maps raw probabilities to calibrated ones. This is critical for the Uncertain tier detection.
  4. Tier Mapping — Calibrated probability maps to tier+confidence: ≥0.80 → MFA_High/high; 0.60–0.79 → MFA_Medium/medium; 0.40–0.59 → MFA_Low/medium; <0.40 → Non_MFA/high. Low confidence score (regardless of tier) → Uncertain/low.
  5. HITL Router — MFA_Medium, Uncertain, and any URL with historical_spend_usd above a configurable threshold are routed to the reviewer queue. The tier and score are stored immediately; HITL does not block the API response.
  6. Explanation Generator — Jinja2 templates (Baseline) render a narrative citing the top SHAP signals. In MVP, Bedrock Claude Haiku generates a more fluent explanation using the same signal evidence as context (no open-web access).

2.4 Signals to Treat with Caution

Anti-pattern 1: Viewability as a sole MFA indicator. MFA sites often score high viewability — they are specifically designed to have ads in-view. Using viewability alone produces systematic false negatives.
Anti-pattern 2: IVT/fraud flags as sole MFA indicator. MFA traffic is frequently human and valid. IVT detection identifies bot traffic, not arbitrage behaviour. These signals are orthogonal, not correlated.
Anti-pattern 3: Homepage-only crawling. MFA sites maintain clean homepages for direct navigation. The article pages under referral traffic are where the MFA behaviour is expressed. Always deep-link into article paths with referral simulation.
Anti-pattern 4: Single-domain blocking. MFA operations span subdomains, reseller nodes in sellers.json, and sibling domains under the same operator. Domain-only signals miss the full network footprint.

3. Architecture Decision Records

ADR-001 — Hybrid Rules + ML + LLM (not LLM-only classification)

DecisionDeterministic rules catch known patterns; XGBoost/LightGBM ensemble for probabilistic ranking; LLM only for explanation generation and RAG answers — never as primary classifier.
RationaleMFA classification needs precision at scale and full auditability. LLM-only classification is ~10–50× more expensive per URL, has latency of 2–5s vs <100ms for rules+XGBoost, is harder to calibrate, and is non-deterministic — making audit trails ambiguous. Industry vendors (IAS, DV, Pixalate) all use multi-signal ML.
Alternatives ConsideredLLM-only classification (too costly, non-deterministic); rule-only (insufficient precision for grey-area cases); random forest (replaced by XGBoost for better calibration support).
Trade-offsMore feature engineering and model maintenance overhead. However, the system achieves lower hallucination risk in classification, fully reproducible decisions, and cost-predictable scaling.

ADR-002 — Page-Section Granularity with 5-Tier Output

DecisionScore per URL path pattern with tiered output: MFA_High | MFA_Medium | MFA_Low | Non_MFA | Uncertain. Action mapping: High → block; Medium/Uncertain → HITL; Low → monitor; Non_MFA → allow.
RationaleANA and DV guidance emphasises shades of gray in MFA classification. A binary domain-level flag either misses borderline cases (too lenient) or over-blocks legitimate publishers (too strict). Homepage is not representative of article experience.
Alternatives ConsideredBinary MFA/Non-MFA flag (insufficient for HITL routing); 3-tier (High/Low/Uncertain) — insufficient for spend-weighted escalation policy.
Trade-offsMore complex action mapping; requires calibrated probabilities for tier boundary decisions. Enables proportional response and reduces false-positive blocking of grey-area publishers.

ADR-003 — Dual-Persona Headless Crawling (Build, not Buy)

DecisionPlaywright cluster with (a) direct navigation and (b) simulated Outbrain/Taboola referrer; 60-second dwell window for ad refresh detection. Build the crawler core; augment with commercial verification APIs (IAS/Pixalate) for traffic signals not observable via crawl.
RationaleReferral vs direct behavioural delta is one of the strongest MFA tell signals per IAB/IAS research. Commercial verification APIs do not expose per-URL dual-persona comparison. Playwright is mature, open-source, and supported in the existing stack.
Alternatives ConsideredBuy-only (IAS/Pixalate APIs) — misses the referral delta signal, vendor lock-in, higher per-URL cost at scale. Puppeteer — Playwright preferred for better browser context isolation.
Trade-offsInfrastructure cost for ECS Fargate crawler pool ($3K–$8K/mo at pilot scale). Legal/robots.txt compliance must be managed. Benefit: proprietary signal generation not available via buy-only path.

ADR-004 — OpenSearch Serverless for Vector Store (AWS Primary)

DecisionOpenSearch Serverless with hybrid BM25 + k-NN retrieval. Metadata filters on domain, url_id, signal_version, doc_type for scoped retrieval.
RationaleHybrid retrieval is required for the RAG use case: exact lookups ("show me signals for domain X") need BM25; semantic search ("sites similar to Y") needs k-NN. OpenSearch Serverless eliminates cluster management overhead. Native AWS integration with IAM and VPC.
Alternatives ConsideredPinecone (fast POC, but vendor lock-in and no hybrid BM25); pgvector (simpler for MVP, but weaker at scale and no metadata filtering at query time); Azure AI Search (documented as Azure equivalent in Section 8); Vertex AI Vector Search (GCP equivalent).
Trade-offsOpenSearch Serverless has cold-start latency for infrequent queries. Cost ($1.5K–$4K/mo at pilot) is higher than pgvector. Benefit: no index management, auto-scaling, production-grade hybrid search.

ADR-005 — LLM Selection — Tiered by Use Case

Decision
Use CaseModel
Explanation generationClaude Haiku / GPT-4o-mini

RationaleTiering LLM selection by task cost profile reduces per-URL explanation cost by ~4–8× vs using Sonnet for all calls. RAG answers benefit from stronger grounding adherence (Sonnet). Guardrail: LLM receives only retrieved JSON evidence — no open-web access in MVP.
Alternatives ConsideredSingle model for all tasks (cost-inefficient); open-source Llama/Mistral on ECS (possible for Production, lower latency but higher infra complexity); GPT-4o via Azure OpenAI private link (documented as primary alternative).

ADR-006 — Event-Driven Microservices (SQS + ECS + Step Functions)

DecisionAPI Gateway + ECS/Lambda for synchronous scoring API; SQS priority queues for async crawl dispatch; Step Functions for batch pipeline orchestration; EventBridge for scheduled triggers.
RationaleDecouples crawl latency (seconds to minutes) from API response time (milliseconds). Enables independent auto-scaling of the crawl worker pool vs the scoring service. SQS FIFO enables spend-weighted priority without custom scheduler logic.
Alternatives ConsideredCelery + Redis as task queue (feasible for MVP, but operational overhead at scale); Kafka/Kinesis (overkill for MVP volumes; documented as OpenRTB stream ingestion path for Production); monolithic synchronous pipeline (blocks API, unscalable).
Trade-offsEventual consistency between submission and result availability. Managed via job status polling (GET /api/v1/jobs/{job_id}). Benefit: linear scaling, fault isolation between crawl and scoring layers.

ADR-007 — Postgres + S3 as Feature Store (Feast Deferred)

DecisionMVP: Postgres JSONB for online signal serving; S3 Parquet for offline training data lake. Feast or DynamoDB deferred until sub-100ms online lookup is required at bid time.
RationaleAt pilot scale (500K URLs/month), Postgres with proper indexing on url_id and Redis caching of recent results is sufficient for the API's throughput requirements. Feast adds operational complexity (feature server, registry) that is not justified until pre-bid latency targets demand it.
Alternatives ConsideredDynamoDB for online serving (Production path when sub-100ms latency required at bid time); Feast with S3/Postgres backend (Production); pure Redis feature store (loses query flexibility).
Trade-offsPostgres may bottleneck at 5M+ URLs/month without read replicas. Redis domain tier cache (24h TTL) mitigates hot-path pressure. Production upgrade path to DynamoDB is documented.

ADR-008 — Integration Strategy (Inbound / Outbound / Buy)

DecisionInbound: DSP CSV/S3 export, REST API, webhook for new domains, optional OpenRTB log sink (Kinesis). Outbound: Blocklist API segment push, pre-bid segment, BI facts (QuickSight/Looker), Slack alerts for high-spend MFA hits. Buy: Traffic enrichment (Similarweb-style) as one signal tier, not source of truth.
RationaleAdvertisers need blocklist segments that plug directly into their DSP. The BI facts table enables spend-at-risk reporting without requiring direct platform access. Treating bought enrichment data as one signal (not ground truth) prevents over-indexing on vendor-biased lists.
Alternatives ConsideredDirect OpenRTB stream integration (Production only — requires Kinesis sink and stream processing); MFA verdict webhooks pushed to DSP (Production — requires DSP partnership).
Trade-offsCSV/S3 batch ingestion has latency vs streaming; sufficient for MVP nightly inventory hygiene use case.

ADR-009 — AWS as Primary Cloud

DecisionAWS as the primary cloud provider. Full Azure and GCP equivalents are documented in Section 8 for organisational flexibility.
RationaleAWS has the most mature ad-tech log processing ecosystem (Kinesis/Glue), OpenSearch Serverless, Step Functions for batch orchestration, and Bedrock for LLM access without custom model deployment. Most of the target organisation's existing infrastructure is on AWS.
Alternatives ConsideredAzure: strong alternative if Azure OpenAI private link is required for LLM; Container Apps for crawler workers. GCP: Vertex AI Vector Search + Cloud Run are viable. Multi-cloud is supported via cloud-agnostic data contracts.
Trade-offsAWS vendor lock-in risk mitigated by using open standards (Postgres, S3-compatible storage, OpenAPI). Service-level abstractions mean switching to Azure/GCP requires infrastructure config changes, not code rewrites.

4. RAG Bot Architecture

The RAG bot provides Ad Ops teams with a natural-language interface to the platform's evidence corpus. It is designed around a strict retrieve-first principle (ADR-001 guardrail): no LLM generation occurs without a retrieved evidence pack. This ensures that every answer is grounded in observed signals, not hallucinated policy positions.

4.5 Anti-Hallucination Pipeline

  1. Retrieve-first: No LLM generation is attempted without a non-empty evidence pack. If the evidence pack is empty, the response is confidence="insufficient" with recommended_action="human_review".
  2. Citation validator: Every factual claim in the answer field must reference a citations[].id that exists in the retrieved pack. The validator rejects the LLM output and escalates if any citation ID is not found in the evidence pack chunks.
  3. Retrieval score threshold: If all retrieved chunks have similarity score below a configurable threshold, the system responds with confidence="insufficient" and does not attempt generation. This prevents low-confidence hallucination on out-of-distribution queries.
  4. Conflicting signals handling: When the evidence pack contains contradicting signals (e.g., high ad density but reviewer override marking Non_MFA), the LLM is instructed to present both sides explicitly in the answer and default to recommended_action="human_review".

4.6 Cost Controls

  • Response caching: Grounded RAG responses are cached in Redis for 24 hours keyed by evidence_hash. Repeated queries about the same URL and signal version are served from cache without LLM invocation.
  • Token caps: Evidence pack passed to the LLM is capped at a configurable token limit (default: 4000 tokens). Large corpora are ranked by relevance score before truncation.
  • Batch indexing: OpenSearch vector indexing for new signal snapshots runs as an off-peak batch job to avoid competing with query traffic during business hours.
  • Model tiering: Explanation generation uses Claude Haiku; RAG answers use Claude Sonnet. Haiku is ~4–8× cheaper per query for structured text output.

5.1 Reviewer Override Protocol

The reviewer override workflow is designed to capture expert human judgment without corrupting the ML model's ground truth labels. Key design decisions:

  • Mandatory reason code enum: Reviewers must select a structured reason code from: false_positive_publisher, referral_delta_expected, policy_exception, insufficient_evidence, vendor_disagreement. Free-text notes are optional and supplementary — they do not substitute for the structured code.
  • final_label stored alongside ML score: The override writes a final_label and override_reason as new fields on the review record. The ML mfa_score, tier, and confidence are never modified or deleted. Both are available for model retraining, audit, and RAG grounding.
  • Dual-control for bulk operations: Any blocklist export covering more than a configurable threshold of domains in a single operation requires sign-off from a second reviewer with admin or reviewer RBAC role.
  • Audit event on every override: Every override call to POST /api/v1/reviews writes an immutable audit event with evidence_hash binding the override to the exact signal snapshot that informed the ML classification.

9.1 Classification Pipeline — ml/src/mfa_ml/scoring/pipeline.py

The classify_snapshot() function is the central orchestrator of the ML pipeline. It implements the cascade pattern (rules → XGBoost → calibrate → tier) and produces a ClassificationOutput that satisfies the platform's output contract.

def classify_snapshot(
    signals: dict[str, Any],
    *,
    evidence_hash: str,           # SHA-256 of canonical signal JSON — for audit binding
    artifacts: ScoringArtifacts | None = None,
    artifact_dir: Path | None = None,
) -> ClassificationOutput:
    """Score a single signal snapshot through the full Baseline pipeline."""

    # Load artifacts from disk if not pre-loaded by worker
    if artifacts is None:
        artifacts = load_scoring_artifacts(artifact_dir)

    # Step 1: Extract only the known CRAWL_FEATURE_NAMES from the signals blob.
    # Extra keys (crawl_ts, schema_version) are ignored — prevents feature leakage.
    features = extract_features(signals)

    # Step 2: Rules engine — deterministic, high-precision.
    # If a rule fires, return immediately with classifier="rules" and confidence="high".
    # No XGBoost inference needed — saves cost and latency for obvious MFA cases.
    rule_match = artifacts.rules_engine.evaluate(features)
    if rule_match is not None:
        return ClassificationOutput(
            tier=rule_match.tier,
            mfa_score=rule_match.mfa_score,
            confidence="high",          # rules are high-precision by design
            top_signals=rule_match.top_signals,
            explanation=render_explanation(rule_match.tier, rule_match.top_signals),
            evidence_hash=evidence_hash,  # binds this output to the crawl evidence
            classifier="rules",
            schema_version="v1.1",
        )

    # Step 3: XGBoost ensemble — returns raw probability in [0,1].
    # predict_proba() uses the feature names in CRAWL_FEATURE_NAMES order.
    raw_proba = float(artifacts.classifier.predict_proba([features])[0])

    # Step 4: Confidence calibration — raw XGBoost probabilities are
    # overconfident. Isotonic regression maps them to calibrated probabilities.
    calibrated = float(artifacts.calibrator.transform(np.array([raw_proba]))[0])

    # Step 5: Map calibrated probability to tier + confidence label.
    # Thresholds: ≥0.80 → MFA_High/high; ≥0.60 → MFA_Medium/medium; etc.
    conf_score = calibrated_confidence_from_proba(calibrated)
    tier, conf_label = map_tier(calibrated, conf_score, artifacts.thresholds)

    # Step 6: SHAP explanation — compute top-5 signal contributions.
    # Uses TreeExplainer on the XGBoost model; positive contribution = MFA evidence.
    top_signals = artifacts.shap_explainer.explain(features)

    # Step 7: Render human-readable explanation using Jinja2 template.
    # In MVP, this step is replaced by LLM generation (Bedrock Claude Haiku).
    explanation = render_explanation(tier, top_signals)

    return ClassificationOutput(
        tier=tier,
        mfa_score=round(calibrated, 4),
        confidence=conf_label,
        top_signals=top_signals,
        explanation=explanation,
        evidence_hash=evidence_hash,  # audit chain maintained
        classifier="xgboost",
        schema_version="v1.1",
    )

9.2 Signal Schema — backend/src/mfa/schemas/signals.py

The SignalFeatures and SignalSnapshotPayload models define the canonical data contract for all crawl-extracted signals. The compute_evidence_hash() function at the bottom of the module is used by every component that needs to bind an audit event to a specific evidence snapshot.

# ── SignalFeatures: all 16 v1.1 crawl features ───────────────────────────
class SignalFeatures(BaseModel):
    """DOM and content-heuristic features extracted by the crawl pipeline.
    
    Null conventions: null = signal not applicable or not measured;
    0/0.0 = measured zero. Never use 0 as a placeholder for missing data.
    """

    ad_to_content_ratio:        float | None = Field(default=None, ge=0.0, le=1.0)
    ads_above_fold:             int   | None = Field(default=None, ge=0)

# ── SignalSnapshotPayload: canonical JSONB document ───────────────────────
class SignalSnapshotPayload(BaseModel):
    """Canonical JSONB document stored in signal_snapshots.signals column."""
    model_config = ConfigDict(extra="forbid")

    schema_version: str = SIGNAL_SCHEMA_VERSION  # "v1.1"
    crawl_ts:       datetime                       # ISO-8601 UTC
    features:       SignalFeatures

    def to_db(self) -> dict[str, Any]:
        """Flatten for Postgres JSONB storage: features merged to top level."""
        data = self.model_dump(mode="json")
        features = data.pop("features")
        data["schema_version"] = SIGNAL_SCHEMA_VERSION
        data.update(features)   # flat JSONB: {schema_version, crawl_ts, ad_to_content_ratio, ...}
        return data

    @classmethod
    def from_db(cls, data: dict[str, Any]) -> "SignalSnapshotPayload":
        """Reconstruct from flat Postgres JSONB row back to nested Pydantic model."""
        known = set(CRAWL_FEATURE_NAMES)
        features = {key: data[key] for key in known if key in data}
        return cls(
            schema_version=data.get("schema_version", SIGNAL_SCHEMA_VERSION),
            crawl_ts=data["crawl_ts"],
            features=SignalFeatures.model_validate(features),
        )

# ── Evidence hash: binds every audit event to exact signal evidence ────────
def compute_evidence_hash(signals: dict[str, Any]) -> str:
    """SHA-256 of canonical JSON for audit binding.
    
    sort_keys=True ensures determinism regardless of dict insertion order.
    separators=(",",":") eliminates whitespace for minimal canonical form.
    Used to: cache RAG responses, bind audit events, verify data integrity.
    """
    canonical = json.dumps(signals, sort_keys=True, separators=(",", ":"), default=str)
    return hashlib.sha256(canonical.encode("utf-8")).hexdigest()

9.3 RAG Service — backend/src/mfa/rag/service.py

The answer_query() function orchestrates the full RAG pipeline. It enforces the retrieve-first guardrail, manages the evidence_hash-keyed response cache, validates citations, and writes an immutable audit event for every query.

async def answer_query(
    session: AsyncSession,
    request: ChatRequest,        # { query, url_id?, domain? }
    *,
    actor_id: str = "anonymous",
) -> RAGResponse:
    """Orchestrate the full RAG pipeline for a chat query.
    
    Pipeline: sanitise → intent → retrieve → [cache check] → 
              ground → validate citations → [cache store] → audit
    """
    # Step 1: Input sanitisation — blocks injection attacks.
    # Raises ValueError on detected injection patterns.
    query = sanitize_query(request.query)

    # Step 2: Intent classification — determines retrieval path.
    # why_mfa → SQL; signal_attribution → SHAP SQL; change_detection → version diff
    intent = classify_intent(query)

    # Step 3: Evidence retrieval — hybrid SQL + OpenSearch k-NN.
    # Always retrieve before any LLM call (retrieve-first guardrail).
    chunks = await retrieve_evidence(
        session, intent=intent, query=query,
        url_id=parsed_url_id, domain=request.domain,
    )

    # Step 4: Resolve evidence_hash from retrieved chunks.
    # Used for: response caching, audit event binding.
    evidence_hash = _resolve_evidence_hash(chunks)

    # Step 5: Cache check — if we've answered this exact evidence state before,
    # return the cached response immediately without LLM invocation.
    cache = get_rag_cache()
    if evidence_hash:
        cached = cache.get(evidence_hash)
        if cached:
            return RAGResponse.model_validate(cached)

    # Step 6: Build grounded response — LLM receives evidence pack ONLY.
    # ADR-001 guardrail: no open-web access; no invented policy rules.
    response = build_grounded_response(chunks, query)

    # Step 7: Citation validation — every claim must cite a chunk in the pack.
    # Raises if any citation ID is not in the retrieved evidence.
    response = validate_citations(response, chunks)

    # Step 8: Cache store (24h TTL, keyed by evidence_hash).
    if evidence_hash:
        cache.set(evidence_hash, response.model_dump(mode="json"))

    # Step 9: Write immutable audit event — every RAG query is audited.
    await write_audit_event(
        session,
        entity_type="rag_query",
        entity_id=str(uuid.uuid4()),
        action="rag.answer",
        actor_id=actor_id,
        evidence_hash=evidence_hash,   # binds audit event to evidence
        payload={
            "query": query[:200],
            "intent": intent,
            "confidence": response.confidence,
            "recommended_action": response.recommended_action,
            "citation_ids": [c.id for c in response.citations],
        },
    )

    return response

9.5 Evidence Hash — Audit Binding

The compute_evidence_hash() function is the linchpin of the platform's audit and integrity model. Its design ensures that any mutation of signal data — however subtle — produces a different hash, making tampered evidence detectable.

def compute_evidence_hash(signals: dict[str, Any]) -> str:
    """SHA-256 of canonical JSON for audit binding.
    
    Canonical JSON guarantees:
    - sort_keys=True: key order is irrelevant; same data always same hash
    - separators=(",",":"): no whitespace; byte-for-byte deterministic
    - default=str: datetime and UUID values serialised consistently
    
    Usage chain:
    1. crawler/: compute_evidence_hash(signals) → stored with signal_snapshot row
    2. ml/worker: pass evidence_hash to classify_snapshot() → stored on ClassificationOutput
    3. rag/service: resolve evidence_hash from retrieved chunks → cache key + audit event
    4. audit/writer: evidence_hash field on every AuditEvent record
    
    This means any audit event can be traced back to its exact signal snapshot,
    and any modification to the signals after the fact is detectable.
    """
    canonical = json.dumps(
        signals,
        sort_keys=True,
        separators=(",", ":"),
        default=str,    # handles datetime, UUID, Decimal
    )
    return hashlib.sha256(canonical.encode("utf-8")).hexdigest()
